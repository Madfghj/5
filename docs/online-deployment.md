# Онлайн-версия OpenCalendar.space

Эта папка содержит второй этап приложения. Проверенная первая версия сохранена отдельно в `OpenCalendar-v0.1-source.zip`. Успешная локальная сборка и зарезервированный адрес сами по себе не подтверждают публикацию.

## Работа при выключенном компьютере

Клиент и API размещаются в облачном Cloudflare Worker, а группы, события, ответы и сессии — в базе D1. После успешного развёртывания сервер работает независимо от компьютера разработчика. Мощность видеокарты или процессора пользователя для работы сервера не требуется.

Изменения в открытом приложении проверяются каждые пять секунд, сразу после собственного действия и при возвращении приложения на передний план. Для общей группы участникам нужен доступ к одному опубликованному серверу. Локальная SQLite первой версии и облачная D1 — разные базы; демонстрационные данные не переносятся как настоящие пользователи.

Новый сайт Sites создаётся с закрытым доступом владельца. Эта внешняя проверка доступа существует отдельно от входа в OpenCalendar. Перед распространением мобильного клиента или приглашением других людей необходимо настроить подходящую аудиторию сайта и проверить API с реального устройства. Доступность страницы не означает, что сторонний мобильный клиент уже получил доступ к API.

## Вход и профиль

При первом запуске интерфейс английский. Пользователь выбирает English, Deutsch, Русский или Français, затем переходит к регистрации. Сохранённый выбор применяется при следующих запусках.

Email и пароль относятся к собственному аккаунту OpenCalendar и не требуют Google. В текущем этапе email не подтверждается отправленным письмом: нельзя выдавать его за проверенный адрес или обещать восстановление письмом до подключения почтовой службы. Пароли должны храниться только в виде медленного salted-хеша; email не должен попадать в списки участников и ответов.

Google, Apple, Microsoft и Telegram включаются только при наличии соответствующих серверных credentials. Настройка их кнопок не создаёт аккаунты разработчика и не подтверждает настоящий вход у провайдера. Telegram требует отдельной настройки в BotFather; подробности — в [messenger-auth.md](messenger-auth.md).

WhatsApp и Signal не выдаются за готовые способы социального входа. Если пользователь добавляет контактную ссылку, это указанный им контакт без проверки владения. В ответах на события показывается имя профиля OpenCalendar, связанное с внутренним user ID.

## Сборка и хранение

Нужны Node.js 24+ и pnpm 11.25.0. Конкретные команды запуска и сборки определяются `package.json`; `pnpm install --frozen-lockfile` устанавливает зафиксированные зависимости. Данные локального preview не являются production-данными.

Облачный артефакт должен содержать Worker ES module `dist/server/index.js`, экспортирующий `fetch(request, env, ctx)`. Встраиваемые клиентские файлы должны быть собраны из той же версии исходников. Нативные оболочки получают клиент через `cap sync`; секреты и облачная база внутрь приложения не копируются.

В `.openai/hosting.json` сохраняется единственный выданный `project_id`, привязка `"d1": "DB"` и `"r2": null`. Для серверного Worker поле `static` не используется. Подключения `DB` достаточно для provision базы через Sites; её внутренний ID не нужно выдумывать или заменять на локальный.

Схема хранится в `drizzle/` вместе с журналом миграций. Миграции содержат ограниченные изменения схемы; пользовательские данные и демонстрационное наполнение не добавляются в миграции. Применённый SQL не редактируется: следующая правка схемы оформляется новой миграцией. Обычные API-запросы не создают и не изменяют таблицы. [Миграции D1](https://developers.cloudflare.com/d1/reference/migrations/)

## Публикация через Sites

1. Проверить тесты, типы и полную сборку. Убедиться, что manifest и миграции включены в исходники.
2. Получить краткоживущий доступ к уже созданному исходному репозиторию. Секрет репозитория передаётся helper через stdin и не сохраняется в файлах или аргументах команд.
3. Helper синхронизирует точные исходники, выполняет необходимые команды и создаёт архив. Он включает `drizzle/` в `dist/.openai/drizzle/`.
4. Сохранить и развернуть именно выданные helper значения `project_id`, `commit_sha` и `archive`. Дождаться terminal-статуса публикации и её фактического URL.
5. Проверить регистрацию, вход, группу с двумя пользователями, три ответа и появление изменений после повторного открытия страницы. Отдельно проверить доступ с телефона, не подключённого к локальному серверу компьютера.

Нельзя подменять публикацию ссылкой `localhost`, ожидаемым адресом до deploy или скриншотом локальной версии. Публикация может применить миграции даже при последующей ошибке загрузки Worker; перед повтором нужно проверить состояние текущей версии.

## Серверные настройки

`PUBLIC_URL` и `CLIENT_URL` должны точно соответствовать опубликованным HTTPS-адресам. Для нативного приложения `VITE_API_URL` — корень доступного API, без завершающего `/api`; после его изменения нужны новая клиентская сборка и `cap sync`. Если веб-клиент и API имеют один origin, веб-сборка может использовать относительный `/api`.

`ALLOWED_ORIGINS` должен содержать фактический web origin и нативные origins `capacitor://localhost` / `https://localhost`. Production OAuth callbacks регистрируются у провайдеров для фактического HTTPS-адреса. Нельзя помещать client secret, Apple `.p8`, пароли, bearer-токены или настройки шифрования в переменные `VITE_*`, manifest, клиентский bundle или исходный архив.

Настройки OAuth сохраняются как серверные секреты через Sites. Пока настоящие ключи не настроены и вход не проверен, соответствующий провайдер должен оставаться недоступным. Доступ и лимиты хостинга зависят от подключённого сервиса и аккаунта; документ не обещает бессрочно бесплатную работу или конкретный SLA.

## Что ещё нужно для магазинов

Папки `android/` и `ios/` — исходники нативных проектов. Они не являются подписанными APK/AAB/IPA. Для Android нужны Java, Android SDK и принятые владельцем условия SDK; для iOS — Mac/Xcode и команда Apple Developer. Для публикации нужны аккаунты магазинов, подписи, реальные контакты поддержки, окончательная политика конфиденциальности и проверка на устройствах.

Перед открытием регистрации широкому кругу пользователей необходимо проверить восстановление аккаунтов, подтверждение email, ограничения попыток входа, удаление данных и резервное восстановление облачной базы. Эти проверки дополняют автоматические тесты и не заменяются наличием рабочего интерфейса.
